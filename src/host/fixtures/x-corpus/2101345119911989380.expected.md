# Berkeley Advanced LLM Agents — Lecture 7: From Perception to Action

∇ Berkeley Advanced Large Language Model Agents — Lecture 7: Multimodal Agents — From Perception to Action

An agent reads two receipts, enters the correct amounts, and clicks Save. Has it completed the task?

Only if the required result is actually there. A plausible screen, a successful click, and a verified saved file are different kinds of evidence. Caiming Xiong's lecture connects that distinction to the environment, training data, and model behind a multimodal agent.

## Let the result decide

Imagine updating a ledger with receipts for 18.50 and 26.40. The expected total is 44.90. Reading the numbers correctly is one step. Entering both rows, saving the workbook, and checking the saved values are separate requirements.

OSWorld makes this distinction operational. A task specifies its initial computer state, instruction, and an execution-based evaluator. The agent interacts with applications, receives new observations, and is evaluated on the resulting state.

There can be several valid routes to the same result. Keyboard shortcuts and menu clicks need not produce the same trajectory. Checking the outcome can accept both. But the evaluator must cover the actual requirement: checking only the total could miss incorrect rows.

## Where do useful trajectories come from?

A tutorial says what to do; it does not necessarily show the exact screen or action needed at each step.

AgentTrek turns tutorials into structured tasks, replays them with an agent in a digital environment, and records the observations and actions. A separate model-based evaluator filters the traces before training. Execution supplies information that a written tutorial lacks, although the filter itself can still make mistakes.

TACO uses actions for a different purpose: improving a visual answer. A model can call OCR, crop a region, or use a calculator, then incorporate the returned evidence. For a receipt showing three items at 12.50 each, OCR plus calculation can support the answer 37.50.

The distinction matters: one pipeline teaches interaction with an environment; the other teaches when an external operation can help answer a visual question. Neither benefits automatically from adding more low-quality traces.

## Knowing what to do is different from knowing where to click

Aguvis brings grounding and planning together. Grounding identifies the target in the current screenshot. Planning chooses the next operation in the context of the goal and history.

Its first training stage develops grounding; the second uses multi-step trajectories with intermediate thoughts and low-level instructions before action generation. A shared visual interface and action format help combine training data across platforms.

In the worked example, an Export button at pixel (800, 450) on a 1000 × 600 screen has normalized coordinates (0.8, 0.75). That standardizes the representation. It does not mean the button stays there after a layout change: the agent still needs the current observation.

![image](https://pbs.twimg.com/media/HSl2dsXakAAGQiA.jpg)

This gives a useful way to read an agent failure. Did it misread the screen, choose the wrong step, miss the target, or fail to produce the saved result? A longer explanation cannot reliably fix a grounding error, and a precise click cannot rescue the wrong plan.

The lecture's deeper connection is that environments, data, and models have to agree on what successful action means. The final message is only one output; the changed environment is where the task's result lives.
