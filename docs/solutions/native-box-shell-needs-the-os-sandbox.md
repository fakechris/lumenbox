# On a host box, a path check on the file routes does not confine the shell

**Symptom.** A native-environment box (`kind: "host"`, `agentbox host up`) refuses `write_file` outside its granted directories, yet `bash` writes to `~/.zshrc`, reads `~/.ssh`, or runs `rm -rf` on a directory nobody granted. The writes are logged as "writes on the person's own machine" and nothing stops them.

**Cause.** `headless.ts` checks paths only for the file routes. `POST /exec`, background jobs and delegated engines (`/acp/open`) all spawn `bash` as the daemon's user. Inside a container that is acceptable because Docker is the wall. On someone's own machine there is no wall. The host-side "review" of those writes was an auto-review verdict in `shadow` mode, which records and never blocks.

**Fix.** Every process boxd starts for an agent on a headless box goes through `confinementFor()` (`src/boxd/confinement.ts`), which wraps it in the `RunOnHost` sandbox (`src/host/host-sandbox.ts`). The sandbox is `sandbox-exec` on macOS and `bwrap` on Linux. Writes are allowed only in rw roots, the work directory, `$TMPDIR` and `/tmp`. ro roots stay read-only even under an rw root. Credential places cannot be read. The only network is the egress proxy. When the sandbox is unavailable, the wrap throws `ConfinementRefused` (HTTP 403) and nothing runs: never fall back to bare. On the host, the policy gate asks before any write on a host box (`hostBoxWrite`, `onHostBox` set by dispatch). Read-only commands do not ask (`shell-readonly.ts`). An operator `allow` rule with `tool:`/`command:`/`path:` lifts the ask. Watch for these:
- Pass the start directory as `runIn`, never as `cwd`. `cwd` becomes writable, so a request with `cwd: ~` would open the whole home directory.
- Seatbelt matches real paths, so resolve everything first. On macOS `/tmp` is `/private/tmp`, and the session wrapper writes `/tmp/boxd-session-*`.
- `bwrap --ro-bind` fails on a path that does not exist. The deny and read-only lists keep only existing paths.
- Under the sandbox, tools and delegated engines that write state under `$HOME` (`~/.npm`, `~/.cache`, `~/.claude`, `~/.codex`) are refused, which made engines unusable on a host box. Do not widen the sandbox to the real home: that hands the box the person's own engine logins. Each agent gets a state directory, `<work>/.state/<agent>` (INV-1710). `confine.wrap()` returns `env` that points `XDG_CACHE_HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `npm_config_cache`, `CLAUDE_CONFIG_DIR` and `CODEX_HOME` into it. Exec, jobs and `/acp/open` merge that env **last**, over the request's env, because the presets name `/home/box/...` homes that do not exist on a host box. `/acp/open` carries `actor: agent:<id>` so an engine's `session/load` after a restart finds the same directory. The person's engine homes (`ENGINE_HOMES_UNDER_HOME` in `host-sandbox.ts`: `~/.claude`, `~/.claude.json`, `~/.codex`, `~/.gemini`, opencode's, `~/.pi`) are hidden and write-denied, like `~/.ssh`. As a result, an engine on a host box has to be logged in from the env the host passes (relay token), or inside its state directory. It never borrows the person's login. The per-agent split is for order, not secrecy: all agents on one box run as one user.
- Hiding files does not hide the macOS Keychain. Claude Code keeps its login there, and git's `osxkeychain` helper keeps passwords there. The Keychain is a service, not a file: `securityd` (`com.apple.SecurityServer`) decrypts the file keychains and `secd` (`com.apple.securityd.*`) the data-protection one. Measured 2026-11-07 with a throwaway keychain under `/tmp`: under the INV-1710 profile a confined `security find-generic-password` read nothing, but only by accident. Security.framework writes its module cache under `$(getconf DARWIN_USER_CACHE_DIR)`, which the box may not write, so every read failed with a Module Directory Service error. With that one directory writable, both `/usr/bin/security` and a small Security.framework client read the fake item, because the profile is `(allow default)` and denied no Mach lookup. With `hideCredentials` the profile now denies the Mach lookups (`KEYCHAIN_SERVICES`, `KEYCHAIN_SERVICE_PREFIXES` in `host-sandbox.ts`), denies exec of `/usr/bin/security` (the agent reads "Operation not permitted"), and hides `~/Library/Keychains`. Denying `com.apple.SecurityServer` alone already refuses the read. A copy of `security` elsewhere is killed by the system, and any other client is stopped by the lookups. Leave `com.apple.trustd` open: certificate checks go there. Under this profile, through a CONNECT proxy on the egress port, curl, a Go binary, `git ls-remote https://…` and node's TLS still verify. `node --use-system-ca` fails, and it already failed under the INV-1710 profile because it reads roots through the Keychain. Node's bundled roots are the default. Do not test this against the login keychain or the search list: a keychain file named with an explicit path exercises the same service.
- The same holds on Linux for Secret Service (gnome-keyring, KWallet). It answers on the session bus, `/run/user/<uid>/bus`, a pathname socket that `--unshare-net` does not cut off. `hideCredentials` hides the whole runtime directory `/run/user/<uid>` (the bus, gpg-agent's sockets, which cache unlocked keys, and the keyring's; since INV-1716 also systemd's user manager, rootless docker and podman, a desktop session's ssh-agent) and `~/.local/share/keyrings`. This is checked in the hermetic test only: no Linux machine with a keyring was at hand.
- Hiding files does not close the Unix sockets (INV-1716). A socket is a door to a process running as the person: the ssh-agent signs with their keys although no key file is read, `docker.sock` is root on the machine, tmux runs what it is sent. Measured 2026-11-07 on macOS with a throwaway `ssh-agent -a /tmp/…` and key and a throwaway echo socket standing in for docker.sock: under the INV-1711 profile a confined `ssh-add -l` listed the key, `ssh-keygen -Y sign -f key.pub` signed through the agent, and the stand-in answered, because the profile ended in `(allow network-outbound (remote unix-socket))`. The macOS ssh-agent lives at a guessable `/private/tmp/com.apple.launchd.*/Listeners` even when `SSH_AUTH_SOCK` is not passed on. Fix, `hideCredentials` only (a `RunOnHost` command is asked for each time and keeps its sockets):
  - macOS: no blanket allow. The only Unix sockets left are under the box's own writable roots, `(allow network-outbound (remote unix-socket (subpath <work dir / rw repository>)))`, never under `/tmp` or `$TMPDIR`, where the person's agent, tmux and editor sockets live. What the confined side needs was measured with every socket refused: curl, `git ls-remote https://…` and node TLS through a CONNECT proxy on 127.0.0.1 (the egress proxy is a numeric loopback address and resolves names itself), `localhost` lookups, npm, python's multiprocessing and node's `fork` IPC (socketpairs, not connects) all work. The egress proxy is TCP on macOS, so it needs no socket. Refused besides the agent and docker: `/var/run/mDNSResponder`, so names are not resolved inside the box. That matches Linux, whose namespace has no DNS either, and closes a DNS channel around the relay's allow list.
  - Linux: bubblewrap cannot filter `connect()`, and `--unshare-net` cuts only abstract sockets, so the socket places are hidden: the whole runtime directory, `SOCKET_PATHS` (`/var/run/docker.sock`, `/run/docker.sock`, podman's), `SOCKET_HOMES_UNDER_HOME` (`~/.docker/run`, `~/.orbstack/run`, `~/.colima`, `~/.rd`, `~/.lima`; hidden on macOS too), the directory of the daemon's `$SSH_AUTH_SOCK` (passed in by `boxd/main.ts`; the socket alone when the directory is the home), and the shared `/tmp` is not there at all (INV-1724). INV-1716 first turned every socket lying in `/tmp` or one level down at the start into `/dev/null`, which left a window: a tmux, ssh-agent or database socket the person opens after a long command or job started was reachable by it. Now `/tmp` and `$TMPDIR` are the box's own directory, `<work>/.tmp` (`privateTmp` in `SandboxRules`, set by `confinement.ts`; an empty tmpfs per command when there is no work directory), so no socket of the person's is ever in it. It persists between commands, so the session wrapper's `/tmp/boxd-session-*` files and an agent's scratch files work as before. The only things bound in are the egress bridges `agentbox-host-port-<n>.sock`, read-only (a read-only mount does not refuse `connect()`, and the box cannot remove or replace its way out), from the directory `HostSandbox.tempDir` names, which `confine.bridge()` listens in, so the two cannot disagree. A bridge must be listening when the command starts: bwrap cannot bind what is not there. A root granted under `/tmp` is bound after the private `/tmp`, so it is still there; nothing else under `/tmp` is named, so the start-up sweep is gone. A `RunOnHost` command keeps the shared `/tmp`. Gap that remains: the hidden places outside `/tmp` are the paths that exist at the start, so a socket made later at a new path elsewhere (a docker socket at a path not in `SOCKET_PATHS`) is reachable.
  - macOS has no such window: Seatbelt checks the path at each `connect()`, and only the box's own roots are allowed, never `/tmp` or `$TMPDIR`. The INV-1724 test runs on macOS too and shows a socket made in the stand-in `/tmp` after the command started refused.
  - Both: `SOCKET_VARIABLES` (`SSH_AUTH_SOCK`, `SSH_AGENT_PID`, `DOCKER_HOST`, `CONTAINER_HOST`, `DBUS_SESSION_BUS_ADDRESS`, `GPG_AGENT_INFO`) are unset inside the wrapper (`/usr/bin/env -u …` on macOS, `unset` in bwrap's shell), so they are gone whatever environment the request carried.
  - A box that needs a socket of its own puts it under its work directory. Do not widen to `/tmp`: that is the person's agent again. Never test this against the real agent or docker; a throwaway `ssh-agent -D -a <tmp>/agent.sock` with a throwaway key shows the same.

**Verify.** `node --experimental-transform-types --test src/boxd/confinement.test.ts`. Its last test runs real commands under the real sandbox where one is available, and is skipped where it is not, including under a sandboxed test runner. It checks that a write outside the roots fails and leaves no file, that a ro root is not writable, that `~/.ssh` cannot be read or written, that `rm -rf` outside the roots removes nothing, that a write to `$XDG_CACHE_HOME` lands in `<work>/.state/a1/cache` while `~/.cache` stays shut, that the fake `~/.claude` and `~/.codex` logins can be neither read nor written, that `npm config get cache` names the state directory, and that a job finds `$CODEX_HOME` in the state directory even when the inherited environment named `~/.codex`. On macOS the next test makes a throwaway keychain in its temp directory with one fake item, reads the item unconfined as a control, and then shows that a confined `/usr/bin/security` does not start and a compiled Security.framework client reads nothing. It grants the user cache directory so that the module-cache accident cannot be what passes, and deletes the keychain afterwards. Disable the Mach deny and that test fails. The INV-1716 test starts its own `ssh-agent -D` in its temp directory, adds a throwaway key and deletes the key file, so a signature can only come from the agent. Unconfined, as a control, it lists and signs and an echo socket standing in for docker answers. Confined, `ssh-add -l` lists nothing even with `SSH_AUTH_SOCK` set by hand, `ssh-keygen -Y sign` writes no signature, the stand-in is unreachable, and a socket the box serves under its work directory still answers. Put the blanket allow back and that test fails. The INV-1724 test starts a confined command that waits, then opens two sockets in the stand-in `/tmp` (one directly, one a level down like `tmux-<uid>/default`), checks they answer unconfined, and lets the command connect: both are refused. In the same test the egress proxy answers through the bridge, a scratch file in `/tmp` is there for the next command (on Linux in `<work>/.tmp`, not the shared one), and on Linux a session's `cd` and `export` carry over with its files in `<work>/.tmp`. In CI on Linux (`CI=true`) the real-sandbox tests run even if the probe says the sandbox is unavailable, so a missing bwrap fails the build instead of skipping. The tests set `HOME` to its fake home, so it never reads the real one. `boxd` started headless logs `commands run under sandbox-exec: …` at start-up. With the sandbox missing, it logs `every command is refused`.
