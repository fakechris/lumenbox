# On a host box, a path check on the file routes does not confine the shell

**Symptom.** A native-environment box (`kind: "host"`, `agentbox host up`) refuses `write_file` outside its granted directories, yet `bash` writes to `~/.zshrc`, reads `~/.ssh`, or runs `rm -rf` on a directory nobody granted. The writes are logged as "writes on the person's own machine" and nothing stops them.

**Cause.** `headless.ts` checks paths only for the file routes. `POST /exec`, background jobs and delegated engines (`/acp/open`) all spawn `bash` as the daemon's user. Inside a container that is acceptable because Docker is the wall. On someone's own machine there is no wall. The host-side "review" of those writes was an auto-review verdict in `shadow` mode, which records and never blocks.

**Fix.** Every process boxd starts for an agent on a headless box goes through `confinementFor()` (`src/boxd/confinement.ts`), which wraps it in the `RunOnHost` sandbox (`src/host/host-sandbox.ts`). The sandbox is `sandbox-exec` on macOS and `bwrap` on Linux. Writes are allowed only in rw roots, the work directory, `$TMPDIR` and `/tmp`. ro roots stay read-only even under an rw root. Credential places cannot be read. The only network is the egress proxy. When the sandbox is unavailable, the wrap throws `ConfinementRefused` (HTTP 403) and nothing runs: never fall back to bare. On the host, the policy gate asks before any write on a host box (`hostBoxWrite`, `onHostBox` set by dispatch). Read-only commands do not ask (`shell-readonly.ts`). An operator `allow` rule with `tool:`/`command:`/`path:` lifts the ask. Watch for these:
- Pass the start directory as `runIn`, never as `cwd`. `cwd` becomes writable, so a request with `cwd: ~` would open the whole home directory.
- Seatbelt matches real paths, so resolve everything first. On macOS `/tmp` is `/private/tmp`, and the session wrapper writes `/tmp/boxd-session-*`.
- `bwrap --ro-bind` fails on a path that does not exist. The deny and read-only lists keep only existing paths.
- Under the sandbox, tools and delegated engines that write state under `$HOME` (`~/.npm`, `~/.cache`, `~/.claude`, `~/.codex`) are refused, which made engines unusable on a host box. Do not widen the sandbox to the real home: that hands the box the person's own engine logins. Each agent gets a state directory, `<work>/.state/<agent>` (INV-1710). `confine.wrap()` returns `env` that points `XDG_CACHE_HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `npm_config_cache`, `CLAUDE_CONFIG_DIR` and `CODEX_HOME` into it. Exec, jobs and `/acp/open` merge that env **last**, over the request's env, because the presets name `/home/box/...` homes that do not exist on a host box. `/acp/open` carries `actor: agent:<id>` so an engine's `session/load` after a restart finds the same directory. The person's engine homes (`ENGINE_HOMES_UNDER_HOME` in `host-sandbox.ts`: `~/.claude`, `~/.claude.json`, `~/.codex`, `~/.gemini`, opencode's, `~/.pi`) are hidden and write-denied, like `~/.ssh`. As a result, an engine on a host box has to be logged in from the env the host passes (relay token), or inside its state directory. It never borrows the person's login. The per-agent split is for order, not secrecy: all agents on one box run as one user.
- Hiding files does not hide the macOS Keychain. Claude Code keeps its login there, and git's `osxkeychain` helper keeps passwords there. The Keychain is a service, not a file: `securityd` (`com.apple.SecurityServer`) decrypts the file keychains and `secd` (`com.apple.securityd.*`) the data-protection one. Measured 2026-11-07 with a throwaway keychain under `/tmp`: under the INV-1710 profile a confined `security find-generic-password` read nothing, but only by accident. Security.framework writes its module cache under `$(getconf DARWIN_USER_CACHE_DIR)`, which the box may not write, so every read failed with a Module Directory Service error. With that one directory writable, both `/usr/bin/security` and a small Security.framework client read the fake item, because the profile is `(allow default)` and denied no Mach lookup. With `hideCredentials` the profile now denies the Mach lookups (`KEYCHAIN_SERVICES`, `KEYCHAIN_SERVICE_PREFIXES` in `host-sandbox.ts`), denies exec of `/usr/bin/security` (the agent reads "Operation not permitted"), and hides `~/Library/Keychains`. Denying `com.apple.SecurityServer` alone already refuses the read. A copy of `security` elsewhere is killed by the system, and any other client is stopped by the lookups. Leave `com.apple.trustd` open: certificate checks go there. Under this profile, through a CONNECT proxy on the egress port, curl, a Go binary, `git ls-remote https://…` and node's TLS still verify. `node --use-system-ca` fails, and it already failed under the INV-1710 profile because it reads roots through the Keychain. Node's bundled roots are the default. Do not test this against the login keychain or the search list: a keychain file named with an explicit path exercises the same service.
- The same holds on Linux for Secret Service (gnome-keyring, KWallet). It answers on the session bus, `/run/user/<uid>/bus`, a pathname socket that `--unshare-net` does not cut off. `hideCredentials` binds `/dev/null` over the bus and hides `/run/user/<uid>/keyring` and `/run/user/<uid>/gnupg` (gpg-agent, which caches unlocked keys) and `~/.local/share/keyrings` (`SECRET_SOCKETS_UNDER_RUNTIME`). This is checked in the hermetic test only: no Linux machine with a keyring was at hand.

**Verify.** `node --experimental-transform-types --test src/boxd/confinement.test.ts`. Its last test runs real commands under the real sandbox where one is available, and is skipped where it is not, including under a sandboxed test runner. It checks that a write outside the roots fails and leaves no file, that a ro root is not writable, that `~/.ssh` cannot be read or written, that `rm -rf` outside the roots removes nothing, that a write to `$XDG_CACHE_HOME` lands in `<work>/.state/a1/cache` while `~/.cache` stays shut, that the fake `~/.claude` and `~/.codex` logins can be neither read nor written, that `npm config get cache` names the state directory, and that a job finds `$CODEX_HOME` in the state directory even when the inherited environment named `~/.codex`. On macOS the next test makes a throwaway keychain in its temp directory with one fake item, reads the item unconfined as a control, and then shows that a confined `/usr/bin/security` does not start and a compiled Security.framework client reads nothing. It grants the user cache directory so that the module-cache accident cannot be what passes, and deletes the keychain afterwards. Disable the Mach deny and that test fails. The test sets `HOME` to its fake home, so it never reads the real one. `boxd` started headless logs `commands run under sandbox-exec: …` at start-up. With the sandbox missing, it logs `every command is refused`.
