# A node's own Mac screen: read the permissions, never ask for them, and keep the shell off the screen

**Symptom.** Three things go wrong when an organisation node opens its Mac's own screen to the `computer` tool (`agentbox node run --screen`, `AGENTBOX_NODE_SCREEN=1` for the app). A dialog ("LumenBox would like to record this computer's screen") appears on a machine nobody is sitting at, and the batch hangs behind it. A capture comes back as only the wallpaper and the menu bar, and the model acts on it. A confined `bash` runs `screencapture` or `osascript` and reaches the screen without the takeover lease, the owner check or the approval card.

**Cause.** Screen Recording and Accessibility are TCC permissions held by the *responsible* app: LumenBox when the app starts the node, Terminal when someone runs it by hand. Every process that app starts inherits them, including the daemon's confined shell. `screencapture` without the permission prompts, or on newer macOS captures only the desktop picture without failing. Events posted without Accessibility are silently dropped.

**Fix.** The driver is `src/cua/macos-executor.ts`. The DisplayManager runs it as desktop 1 through `src/boxd/native-screen.ts`.
- Every batch starts with the helper's `state`: `CGPreflightScreenCaptureAccess()` and `AXIsProcessTrusted()`. Both only read and never prompt. A missing permission is `PERMISSION_DENIED` before any capture or input (`not_delivered`). `screencapture` runs only after the read said yes. Never call `CGRequestScreenCaptureAccess`, `AXIsProcessTrustedWithOptions` with the prompt option, or System Events (Automation prompts too). `macos-executor.test.ts` fails if the helper source names any of them.
- After a batch that wrote, `state` is read again. A permission withdrawn mid-batch is reported as an error after dispatch, which reads as unknown, never as done.
- CoreGraphics posts in points and `screencapture` captures pixels (twice as many on Retina). The scaler maps API space to the main display's bounds in points, `sips --resampleWidth` brings the capture to API width, and the result is a PNG (`screenshot_media_type: "image/png"`, which the host passes to the model as such).
- Where the screen is open, the confined shell's Seatbelt profile refuses to exec `SCREEN_PROGRAMS` (`screencapture`, `osascript`, `osacompile`, `automator`, `shortcuts`). The host's shell guard also refuses `screencapture`, alongside `osascript` and `cliclick`. A rule on a path stops neither a copy of the program under another name nor a program the agent compiles itself, so the profile also refuses what such a program reaches the screen through (INV-1756): the Mach services in `SCREEN_SERVICES`, each under its global and its local name, and the IOKit user client in `SCREEN_USER_CLIENTS`. A box whose screen is closed, and a Docker box, get none of this.
- **What was measured, and where.** On hosted CI runners (macOS 15.8 and 26.7, arm64, a console session holding Screen Recording, Accessibility and event posting), 2026-11-19, with `scripts/screen-wall/measure.sh`: each way in run bare, then under a profile that allows everything and reports every lookup, then with each reported service refused alone, then under the daemon's own profile. It was never run on a person's machine and must not be: a refusal that is wrong posts input into their session. The script refuses to start anywhere but a hosted runner or an account named as a throwaway.

  | Way in | Stops when this alone is refused | Under the open-screen profile |
  |---|---|---|
  | `CGEventPost` (an input event) | `com.apple.windowserver.active` | refused, pointer did not move |
  | `CGWarpMouseCursorPosition` | `com.apple.windowserver.active` | refused |
  | `IOHIDPostEvent` (no window server involved) | IOKit open of `IOHIDParamUserClient` | refused |
  | `CGDisplayCreateImage`, `CGWindowListCreateImage` | `com.apple.windowserver.active`, or `com.apple.replayd` | refused, null image |
  | ScreenCaptureKit screenshot | `com.apple.replayd` (it works without the window server) | refused |
  | `CGWindowListCopyWindowInfo` (window titles) | `com.apple.windowserver.active` | refused |
  | Accessibility (`AXUIElementCopyAttributeValue` on another app) | `com.apple.axserver` as a **local** name; the global-name rule does not stop it | refused |
  | a copy of `screencapture` under another name | `com.apple.windowserver.active`, or `com.apple.replayd` | refused |
  | a copy of `osascript` telling System Events to press a key | nothing of ours: it works bare and is refused under any Seatbelt profile, even one that allows everything | refused |

  Under the closed-screen profile every row but the last got through, which is the hole this closes. curl, git, node, npm, python3, clang and swiftc (network through a loopback proxy, as in a box) ran the same with the screen closed and open on both runners; so did all of them but npm, and go, on a macOS 14.6 machine, where npm reaches its registry under neither profile (`scripts/screen-wall/ordinary.sh`, which touches no screen and may be run anywhere).
- **What was not measured.** macOS 14 and earlier have no hosted runner, so the refusals themselves are unproven there; only the ordinary commands were run on 14.6. A virtual HID device (`IOHIDUserDeviceCreateWithProperties`) and the render server (`CARenderServerRenderDisplay`) did not work bare on the runners, so nothing shows whether the profile would stop them. The profile is `(allow default)` with a list of refusals: it stops the ways in that were found, and a way nobody thought of is not on the list. `com.apple.tccd.system` and `IOSurfaceRootUserClient` also stop a capture when refused, and are left open because ordinary programs use them. What refuses a GUI program is also what refuses these: a confined command cannot open a window where the screen is open.
- The default helper is JXA run by `/usr/bin/osascript`, with the request on stdin. A node can name a signed helper that speaks the same requests with `BOXD_NATIVE_SCREEN_HELPER`. Typing goes through `CGEventKeyboardSetUnicodeString`, one character at a time, so that text with no key on the layout, such as Chinese, is typed as text. That JXA bridging has not yet run on a real Mac: the check by hand below is its first test.

**Verify.** `node --experimental-transform-types --test src/cua/macos-executor.test.ts src/boxd/native-screen.test.ts` uses fake hands: points scaling, the PNG at API width, refusal before dispatch for each missing permission, a mid-batch withdrawal, takeover and stop stopping the batch at the next input, one agent at a time, and the screen never reaped. Nothing in `npm test` touches a real screen. On a real node, by hand: with neither permission granted, a `computer` screenshot answers PERMISSION_DENIED naming Screen Recording, and **no dialog appears**. After granting both and restarting the node, a click lands where the screenshot shows it, `type` puts `订单 42` into a text field, and `cmd+s` saves. Take over from Settings and the agent's next input is refused USER_IN_CONTROL. Withdraw Accessibility in System Settings and the next batch is refused. Stop the node and nothing more moves. In the box's shell, `screencapture /tmp/x.png` prints "Operation not permitted". The wall against a program of the agent's own is proven by the `screen-wall` workflow (`.github/workflows/screen-wall.yml`), which runs `measure.sh` on hosted macOS runners when the profile or the measurement changes, or by hand, and fails if anything gets through the open-screen profile, if no way of posting input worked bare (a run that would prove nothing), or if an ordinary command is lost. `npm test` only proves the profile names the refusals (`src/boxd/confinement.test.ts`). Run it again for a new macOS before believing the list there.
