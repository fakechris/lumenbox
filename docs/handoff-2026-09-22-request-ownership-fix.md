# Handoff — 吞单边界修复与 INV 合同校正

## 结论

吞单边界可以修，不需要再加“必须完成”的提示词。这次取消聊天入口的隐式合并和后台转发路径，每条普通请求、显式回答、显式追加都进入可追踪的独立任务。修复在 `fix/request-ownership-delivery` 分支，基于已部署的 `23f51fd`；本次代码尚未合并或部署，不能把上一次 PR #205 的上线当成本次上线。

## 这次复现和修复

1. **待回答问题吞掉新请求。** 修复前，旧任务阻塞时设置待回答问题，再发 URL、“另外介绍…”、“同时支持…”、“好”，测试预期 5 个任务，实际只有 1 个。原因不是模型：`awaitingAnswer` 让下一条任何输入成为旧任务的 continuation，且词法判据继续误判其余输入。已删除词法推断和 channel `steer` 接口。
2. **回答没有归属。** `/answer <questionId> 答案` 和问题卡片必须核对发送人、渠道、会话、指定 agent、期限；只消费一次。普通新消息不清问题。提问按原始会话与 principal 查发送位置，不再只取该 agent 最后一个聊天对象。问题卡按钮的“停”“桌面”等词作为答案，不触发控制命令。已接受答案立即写问题账本，重启不重新执行其默认选项。
3. **结束瞬间的后台转发。** `/continue <taskId> 内容` 校验目标后建立可见的后续任务，引用原任务，排队完成后单独回复。不再只说“带到了”。不支持把追加即时塞入当前模型轮次；这是明确的体验取舍。错误、其他人的、其他会话的、排队中或已结束的目标会被拒绝，并提示单独发送新请求。
4. **排队期间混入其他任务的回答。** 旧代码用请求到达时的转录下标读取之后所有助手正文；排队时旧任务也可能在这个区间。新聊天回复及新恢复记录按 `messageId → causedBy → turnId` 取正文。没有对应归属时不借用别人的回答。无 messageId 的历史恢复记录仍兼容旧规则。
5. **未投递却完成。** 飞书缺少客户端/目标、缺少 message ID、正文发送失败、附件失败都会显式失败。任务只在正文及附件发送成功后结算；开场白恰好等于最终答复时，也要等待开场白发送结果。发送结果不明时取消本次调用的盲目重试及 reply→create 降级，避免双写。附件失败不会标成已送达，也不会在同次调用中再走“正文提到的文件”补发。
