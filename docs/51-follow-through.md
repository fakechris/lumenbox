# 51 · 跟进（follow-through）：问题、承诺与挂着的工作如何不再无声

*2026-09-14。起因是线上一份周报：Q1–Q5 挂了四周没人答，"9/11 前发 reminder"写了没发，t12 该关没关，review 队列四条挂一两周。本文给出我们自己的高层方案，先说别的系统怎么做，再说已经落地的东西，最后是把这些拧成一个模型的设计。*

*v2（同日）：初版的四条 rail 经过 codex（gpt-6-astra）对着真实代码做的对抗性 review，
被找出六处会造成实际伤害的漏洞——其中两条已经在线上发生。六处都已修（INV-530…535，
PR #151–#156），本文按修完之后的事实重写；§5 记录了 review 改变了哪些设计判断，因为
"当时为什么那样想"比"现在是什么样"更难重建。*

## 0. 一句话

**挂着的东西不是状态，是一种会到期的对象。** 问题、承诺、任务卡、提案，每一个都带一只表；到点没人动，系统按事先说好的默认动作处理并出声，而不是继续挂着等人。人的沉默被解释成三种之一——"按默认"、"跳过"、"不反对"——由对象类型决定，绝不解释成"同意关掉工作"。

**而沉默要先成立。** v2 加的一句，是整份方案里最贵的一句：*没送达就不是沉默，等待也不是沉默。*
一条推不进群的提醒、一个被问的人根本没看到的默认、一张 blocked 在别人那里的卡，都不构成
"这个人没回应"。系统只能对**确实到达了某个人、而那个人确实没动**的东西行使到期权力。

## 1. 别人怎么做（本地源码核对，引用见 docs/research/）

| 维度 | Hermes（`~/sdcard/source/hermes-agent`） | OpenClaw（`~/sdcard/source/openclaw`） | Grok Bot（research/GROKBOT-*） | Argus（research/ARGUS-*） |
|---|---|---|---|---|
| 没人答的问题 | `clarify` 3600s 超时，哨兵答案"用你的判断继续"；`timed_out` 区分跳过与走开；批量问题超时即中止其余；无每会话预算，只有 prompt 劝导；headless worker 禁止提问 | `ask_user` 900s（30–3600）到期 `no_answer` 继续；一会话只允许一个待答问题；**用户随便说一句就被当作答案**；审批超时默认拒绝 | 提问 widget 会过期："moved on without responding — treat it as skipped" | 不问人；Reviewer 裁决 |
| 挂着的工作 | SQLite kanban，无 due；只对 running 做租约回收；阻塞超 24h 只在"按需诊断"里出现，不推送；两次同因 block 升级到 triage；不自动归档；agent 无归档工具 | 两套登记（background tasks / workboard），都按 last-update 老化，无 due；staleness 只是被动诊断（blocked 超 24h "needs attention"），不推给人；suggestion 卡 process-local、无老化、重启即丢 | Involute claim 2h 租约 | 任务/检查点/决策全持久化；Reviewer 说 done 才 done，没有"挂着"这个状态 |
| 未来承诺 | 有 cron（自排 reminder/一次性），但让承诺落地的机制是**回合内**的"绝不以承诺结束回合"（stop-nudge，预算 2）；没有把"by Friday"变成 job 的机制，也不事后对账 | 两个显式机制：automations（at/every/cron）与 standing intents（事件触发的前瞻记忆，24h 冷却、最多 3 次、90 天过期）；都靠显式调用，**不从口头承诺生成**；job 的失败有告警/自动停用，但没有"口头承诺是否产生了 job"的检查 | 例程 = skill 文件的 schedule/trigger | Planner DAG + acceptance_check |
| agent 能否提议关闭 / 沉默怎么算 | 只能把工作挪进人面向的 lane（typed block、triage、suggestions）；不能自关；suggestions 永不过期；**沉默 = 一直挂着** | `dismiss_task` 只能撤回自己的 suggestion；workboard 可 complete/block/move 不能归档；"Cancellation is always explicit"；**沉默从不等于同意关闭**；沉默能关掉的只有机器超时（no_answer、审批 deny、task lost） | — | — |

**共同点**：都把"问题超时→按默认继续"做成了硬机制；都**没有** due 日期；都把工作项的老化做成被动诊断而不是推送；都没有把口头承诺对账成 job；都不让 agent 自己把工作关掉。**我们的差异**：我们已经有例程（`schedule:`/`@at`/`trigger:`）、任务板、提问卡、reconcile 这条 rail（docs/29 模板）——缺的正是"对象带表"和"沉默的解释"。

WorkBuddy / 豆包 Work（binary 静态检查，docs/research/2026-09-14-workbuddy-doubao-binaries.md）：**WorkBuddy 5.5.6** 的 asar 里有完整的一套：审批 `DEFAULT_APPROVAL_TIMEOUT_MS = 120s`、`autoRejectOnTimeout: true`、注释写明「文本审批超时：自动拒绝，并同步通知 agent 与 IM」，UI 叫「授权超时未确认」；无人值守的定时任务遇到 AskUserQuestion 直接 `cancelQuestion`（「后台定时任务无人值守…已自动跳过」）；定时任务是一等功能（`automation.tab.scheduledTasks`，按固定时间拉数据批量建待办）；待办有 `dueDate`，但**没有**找到逾期推送、自动归档或老化提醒的字符串。即：沉默在它那里=**拒绝**，比 Hermes/OpenClaw 更保守，而挂着的工作同样只有 due、没有推送。**豆包 Work** 是站点化 Chromium 壳，逻辑在服务端，本地无可核对的产物，扫 Service Worker 缓存只命中无关内容——不下结论，也不算作反证。

Octop（`~/sdcard/source/Octop`，TencentCloud，Python，多用户多 agent，docs/research/2026-09-14-octop-follow-through.md）：
形状与我们最近的一家。HITL pending 表 TTL 30 分钟、**惰性过期、到点什么都不做**（不按默认、
也不拒绝，人晚了回来只看到"已过期"）；一会话只允许一个 pending，新的把旧的显式置为
`expired` 而不是覆盖；问题有 id，`/approve <id>`；`resolve_ask_pending` 的 docstring 写着
它会对"**同一个群里问给另一个人的问题**"返回 None——和我们 INV-533 修的是同一条判定。
定时投递在目标会话的锁里跑并校验 `session.user_id`，产物是会话里的一对规范消息。
挂着的工作这一维和其他几家一样：没有 due 的推送、没有老化、没有归档。

## 2. 已经落地的东西（2026-09-14，PR #145–#148 与 #151–#156）

四条 rail，加上对抗性 review 之后的六处修正。每条写的是它现在的样子，不是初版的样子。

1. **问题会过期（INV-526 + INV-533）**。每个 AskUser 被看守：默认 4 小时，agent 可设 5 分钟到 7 天。
   问题有 id，并记住**被问的是谁**——只有那个人的回复算回答，群里另一个人说什么都不算
   （初版把"该会话里此后有任何人发言"当成回答；同一个坑 Octop 的 docstring 里写着）。
   同一会话的第二个问题不是覆盖，而是给第一个一个 `superseded` 的判决。到期有默认值 →
   唤醒 agent 按默认走并在**提问的那个群**里说一句；无默认 → "对方已经 moved on，视为跳过"。
   卡片上写着到期会怎样、到什么时候（`questionTerms`）——没告诉过人的默认不算默认。
   `questions.jsonl` 既记提问也记判决，重启后待答问题连同它的钟一起恢复。
2. **任务板 due 与老化（INV-527 + INV-530 + INV-532）**。Task 有 `due`；过期或 7 天没动的
   **open/doing** 卡，每 48 小时向请求者敲一次（close / downgrade / continue），敲两次没动
   第三次归档为 dropped。三条限定是 review 加的：
   **(a)** 提醒必须真的送到——通知按 conversation directory 解析地址，`tryPushToChat` 报告
   是否送达，**送不到就不计数**（初版把 conversation id 当 chatKey，飞书群一条都没收到过，
   而计数照加、两次之后照样归档）；
   **(b)** `blocked`、`review`、`waiting_on`、due 还在未来的卡**只提醒不归档**，敲到上限就安静；
   **(c)** `snooze_until` 让"现在不行，X 日再看"成为一个可以说出口的答案。
3. **承诺对账（INV-528 + INV-534）**。例程报告里的 `## 下周改` / `## Next week` 块逐条对照
   看板与例程表。载体必须**是活的卡，或在承诺写下之后才完成的卡**（初版会拿上周已完成、
   甚至已 dropped 的同名卡交差）；`by 9/19` 不再被 9/20 到期的卡满足（一天容差已删）；
   每条承诺**绑到上次的 task id**，重复的承诺不会漂到别的卡上；修复 cue 跑完之后宿主
   **再对一次账**并记录那个结果（agent 说"建好了"是一句话，账本记的是存在的东西）；
   本周没重申、也没做完的承诺**继续携带**到下次开头；`runNow`、webhook 与定时走同一条路径。
4. **assignee 可提议关闭（INV-529 + INV-531）**。**只有 assignee** 可以提议（初版只拦了
   requester 本人，任何 agent 都能给别人的卡上 48 小时的钟），且**卡至少存在 24 小时**——
   一个还没看过看板的人的沉默不是这条规则说的那种沉默。提案记住它是针对**当时那张卡**的
   （标题/状态/due/负责人/评审人/描述的指纹），任何一项变了，提案作废并留一行历史，
   而不是在旧钟上关掉。另外：`dropped` 现在和 `done` 一样有门——只有 requester、reviewer、
   看板和老化 sweep 能丢卡，agent 只能提议。
5. **跟进预算（INV-535）**，第五条，是 review 逼出来的。把所有主动发言分成两类：
   **ask**（要人回答的）可以等——每个房间每滚动 24 小时最多 2 条、每条最多 5 项，多的只报数量；
   **act**（宿主报告它已经做了什么：按默认走了、归档了、关掉了）**永远不压**，只合并——
   做、说、留痕是一件事，压掉"说"会让系统既更安静又更不诚实。一次 sweep 里同一个房间的
   所有条目合成一条消息；被压住的 ask 不计作"已提醒"，所以不会因为没发出去的提醒而归档。
   人回了一句 continue，钟也重置——初版只清计数不清钟，一小时后同一个问题又来一遍。

## 3. 设计：一个模型，四种对象，三种沉默，一个前提

### 3.0 前提：沉默要先成立

到期规则只对**确实送到了某个人、而那个人确实没动**的对象生效。三种情况不算沉默，v2 之前
它们都被算成了沉默：

- **没送达**。地址解析不出来、渠道被换过、adapter 没配、vendor 报错——都不计数，下一轮再提。
  实现上这要求投递函数说得出"到底送没送到"（`tryPushToChat`），而不是吞掉失败返回成功。
- **问的不是这个人**。群里另一个人说话不是回答；被问的人没看到卡片不是"他选择不答"。
- **在等外部**。blocked、review、`waiting_on`、due 还在未来——不动是等待的样子，不是弃单的样子。

### 3.1 对象与表

| 对象 | 谁创建 | 表 | 到期动作 | 沉默的含义 |
|---|---|---|---|---|
| 问题（Question） | agent 向**某个人** | 4h（可设 5min–7d） | 有默认→按默认；无默认→跳过 | "按默认 / 跳过"（仅限被问的那个人的沉默） |
| 承诺（Commitment） | agent 对自己 | 条目上的日期（当天 23:59:59Z，无容差） | 到期前必须有活卡 + 提醒；否则对账时出声，并继续携带 | 不适用（承诺不等人） |
| 任务卡（Task） | 人或 agent | `due`，或 7 天无动 | **open/doing**：敲 2 次→归档；其余：敲 2 次→安静 | "不反对归档"（仅限可归档的那类） |
| 提案（Proposal：关闭 / 建议） | assignee 向 requester | 48h（关闭，且卡 ≥24h）；建议类不过期但有上限 | 关闭提案→生效；建议→留着但不 nag | "不反对"（仅限关闭）/ "留着" |

原则：**每个对象在创建时就把到期动作写死并告诉人**（问题的默认值和截止写在卡上、承诺的日期、
提案的截止），到期不需要再判断；到期动作一律"做 + 出声 + 留痕"，三者缺一不可；出声的地方是
对象来自的那个会话，不是全局面板，也不是"最近找过这个 agent 的人"。

提案还要记住它是针对**当时那个对象**的：卡变了，提案就不是原来那个提案，作废重来。

### 3.2 出声的总量：ask 与 act 分开算

四条 rail 各自都很克制，加在一起不是。所以把主动发言分成两类，只对其中一类设预算：

- **act**（宿主报告它已经做了什么）永不压制，只合并——压掉"说"会让系统既更安静又更不诚实。
- **ask**（要人回答）按房间限流：滚动 24h 两条、每条五项，其余只报数量；被压住的 ask
  不算"已提醒"。

一次 sweep 里同一个房间的所有条目合成一条消息；act 出门时顺路把 ask 带上（打扰已经发生了）。
预算跨重启保留。

### 3.3 "注意力账本"：缩到 retro 需要的那一块

初版想把四份 ledger 并成一个 `/api/attention` 视图，每回合注入 prompt。对抗性 review 的
意见是**过度设计**，我们接受：socket 掉线是基础设施故障，任务在等人是业务状态，两者可以共用
投递出口，**不能共用关闭语义**；每回合全量注入则是让每个 agent 每回合读一遍全局待办。

保留的是最小的那块：**例程的状态投影**——下一次运行前，宿主按上次绑定的 task/job id 读出
状态，确定性地渲染第一段，再接模型的分析。9/21 的 retro 第一段应该是宿主算出来的，不是
模型"记得"要写的。按需的全局视图等有人真的要了再做。

### 3.4 例程作为承诺的载体

例程（skill 文件的 `schedule:`/`@at`）是我们唯一能让 agent"在未来某刻动"的机制，所以：

- retro 类例程的输出**必须**有承诺块（模板 skill 里写死格式），并允许"本周无新增承诺"；
- 承诺块里每条要么自带日期，要么由对账 cue 逼出一个 `@at`；每条绑一个 task/job id；
- 例程的下一次运行以上次承诺的状态开头，包含**没重申但也没做完**的老条目；
- 三个触发入口（定时、手动 runNow、webhook）走同一条路径——否则"点一下立即运行"测不到这套。

**仍未闭合的一点**：`task-due` 现在被当作"有提醒"，但 due 到期只会催 requester，不会唤醒
agent 去执行那个承诺。"有人负责 / 已调度 / 已执行"三者还没分开。要做 agent 自己在未来动的
承诺，载体应该是 `@at` 例程而不是卡；下一轮处理。

### 3.5 边界

- **不做**"从任意口头话里抽承诺"：只认报告里的承诺块。Hermes/OpenClaw/Octop 都不从 prose
  生成 job，我们也不；不确定的抽取会制造假承诺。
- **不做**自动帮人答问题以外的事：到期按默认是 agent 自己声明、且卡片上写给人看过的默认，
  不是系统猜的。
- **不让 agent 归档**：`dropped` 和 `done` 同级有门，agent 只能提议，且每次都留痕、可撤销。
- 沉默永远不等于"同意做某个不可逆动作"：INV-403 的不可逆门不受任何到期规则影响。

## 4. 下一步（按对抗性 review 之后的排序）

- **E. 真机验证（第一）**：让线上那个周报例程跑一次，三条路径都跑——定时、手动 runNow、
  中途重启，看 9/21 retro 的第一段是不是"上次承诺现在各自怎样"。上面每一条反例都应该
  先变成验收项。
- **B. retro 模板 skill（第二）**：承诺块格式、默认值 yes/no 卡、`@at` 例程、"本周无新增承诺"
  的写法，写进 catalog 的 retro skill，让对账有稳定输入。
- **C. 建议类提案的上限与去重（保留）**：Hermes 的 `MAX_PENDING=5` + dedup latch。INV-535
  管的是跟进通知，agent 主动提的新工作/自动化还没有上限。
- **A. 缩小（原"注意力账本"）**：先做 §3.3 的例程状态投影，`/api/attention` 与每回合注入
  等到有人要。
- **D. 砍掉（原"老化 sweep 并入 INV-135"）**：只复用持久化的投递出口与预算；机器故障与工作
  取消分开裁决。

## 5. 对抗性 review 改了什么（2026-09-14）

把 v1 的 §2/§3 交给 codex（gpt-6-astra，high，能读我们的真实代码）做红队。它给了 10 条，
逐条回代码核对后有 6 条成立并已修复——其中两条当时正在线上发生：

| # | 它说的 | 核对结果 | 修在哪 |
|---|---|---|---|
| 1 | 老化通知发不出去但计数照加，静默归档 | **成立**，且是 `server.ts:1626` 早已修过一次的同一个 bug（conversation id ≠ chatKey） | INV-530 / PR #151 |
| 2 | "不让 agent 归档"没落地，`dropped` 无门；proposeClose 不限 assignee、不限卡龄 | **成立** | INV-531 / PR #152 |
| 3 | blocked/review/等外部/未来 due 被当作弃单 | **成立**，与 §0 直接冲突 | INV-532 / PR #153 |
| 4 | "已回答"没有主体；重启丢待答问题；卡上没有默认与截止 | **成立** | INV-533 / PR #154 |
| 5 | 承诺对账验的是"像有安排"：旧卡/已 dropped 卡能交差、一天容差、cue 后不复查、未重申即消失、runNow 不走这条路 | **成立** | INV-534 / PR #155 |
| 6 | 四条 rail 没有共同预算；continue 不重置钟 | **成立** | INV-535 / PR #156 |

没有采纳的：把关闭提案彻底改成"必须人明确同意"（Chris 已就沉默=不反对做过决定，且现在
有送达前提、24 小时门槛与指纹失效三重限制）；把 `/api/attention` 做全（缩成 §3.3）；
把所有老化统一进一个 sweep（§4 D 砍掉）。
