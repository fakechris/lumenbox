### Claim-verification review: 4 fatal, 9 major

Findings I consider load-bearing, each with the reviewer's evidence:

1. **FATAL — the box class is keyed by the wrong thing in the deployment that matters.**
   `classifyBox` is called with `provisioner.boxName`, which for an *attached* provisioner
   is the **URL**. `docker/box/entrypoint.sh` sets `AGENTBOX_BOXD_URL=http://127.0.0.1:1337`
   in every in-box orchestrator, so every `--with-host` box on every host looks up
   `config.boxes["http://127.0.0.1:1337"]`. The `agentbox-box` / `agentbox-acme` entries in
   the live config are **dead config** there, and the first box anyone marks private would
   mark all of them. The label works on the host and not inside the box.
2. **FATAL — §5's shared-memory filter would be installed in the wrong place.**
   `readSharedMemory()` has two more callers besides `turn.ts:906`: `Recall` with
   `shared: true` and `RememberFact`, both model-facing. A filter at the prompt leaves an
   agent able to query across boxes directly.
3. **FATAL — schedules are keyed by skill slug, not agent id**, so §5's "every store keyed
   by agent id is thereby keyed by box" does not cover them. `defaultAgent()` resolves to
   the alphabetically first agent in the whole installation.
4. **FATAL — the roster, task board and claims are unfiltered too.** Every agent's name, id
   and description render into every prompt; `Tasks list` has no assignee filter; claims are
   keyed by work description.
5. **MAJOR — the noVNC "Take over" tab carries no badge and no notice.** It is the surface
   a person actually types a password into, and §1's "rendered wherever somebody is working
   in the box" does not hold there.
6. **MAJOR — `docker/box/hostd.mjs` is a 7.4 MB untracked build artifact** containing
   neither `classifyBox` nor the notice. A `--with-host` box running it shows no badge until
   rebuilt. "Steps 1–3 are done" is true of `src/`, not necessarily of a running box.
7. **MINOR — `web/server.ts:288` builds the provisioner outside any `try`**, so the new
   token refusal kills `startWebServer` instead of degrading to "no box".

The reviewer also verified a long list of claims as **true**, including the boxd upgrade
authentication, per-container volumes, the absence of `--privileged`, the agent prompt
paragraph on both vision paths, and that no path creates an agent outside `registry.create`.

### Design review: 7 fatal, 5 major, 1 minor

The ones that change what should be built:

1. **The takeover fence defends a threat §7 defines out of existence.** §3 accepts "an
   agent that deliberately runs its own reader" as residual; §7 says an injected agent
   reaches the box. What remains is an *accident guard*, which is what this codebase
   honestly calls the same shape elsewhere. Using "fail-closed" borrows authority.
2. **The harness is the leak, not the agent.** `HARNESS_ACTORS` (`channel`, `restart`,
   `host`, `web`, `audit-guard`), `mcp:<principal>` running bash through the singleton box
   client, and inbound channel routing via `registry.list()[0]` are all initiators with no
   agent identity and therefore no box. §5 found one exception and declared the rest
   irrelevant.
3. **The shared label names a set the system cannot enumerate.** `group` is free text; real
   membership lives in Feishu/DingTalk and changes with no event here. §3.1 claims "the
   label is true every time somebody looks at it" — it is unaudited free text.
4. **The class is on the container; the authority is not.** `RunOnHost` executes on the
   operator's machine; vault grants are by `agent:<id>` — "whichever person is driving it",
   which in a shared box is the group; scopes are installation-global and `scopeId` **is**
   on `update`'s mutable allow-list. And §7's claim that use-without-seeing a credential is
   "not offered" is false: the vault plus `RunOnHost` is exactly that, already shipped.
5. **Revoke-and-wipe is unimplementable as written.** The host backup is one recursive copy
   of all of `~/.agentbox`, so you cannot hand one owner their archive without handing them
   everyone's transcripts and `vault.json`, nor delete theirs without destroying everyone's
   restore point. `BoxManager.down({remove:true})` does not pass `-v`; volumes survive.
6. **`boxName` is a string, not an identity.** Destroy and recreate a box with the same name
   and it inherits the old world's class, token, agents, scopes and schedules.
7. **`4 → 5 → 7` produces a second container, not a private box** — what makes it private is
   6, 8, the memory filter and the `SendToAgent` decision, all of which that sentence defers.
   Step 4 also rests on S-2/S-3 (no TLS, plaintext password list), unnamed as prerequisites.

**The thing the document is still avoiding**, per the reviewer: the cheapest resolution may
already be shipped. If credentials that matter live in the vault and reach their target
through the host, the private box's headline use case largely evaporates. The document never
runs that comparison — and running it might conclude the honest shared box plus a better
vault beats the private box. Relatedly: **docs/18 has no user.** Nobody has said who asked
for a private box or what they were trying to do.

**Genuine closures this round**, strictly counted: the `AskUser` correction, and the
shared-box retraction-plus-label. Two rows of §2's table were *reworded*, not closed
(`runArgs` still defeats both "invariant" rows).

## 5. Two live operational gotchas

**The server only starts from a shell that has the model key.** `MINIMAX_CODE_CN_API_KEY`
is not in `config.env`. A launch without it dies with `MissingCredentialError` from
`provider.ts:463` inside `startWebServer`. Today this was misdiagnosed as "the DingTalk
merge broke it" — it did not; the merge is fine and its tests pass.

**Restarting can leave the bot deaf and silent** (roadmap **R35**). Kill and immediately
relaunch, and Feishu still has the dead process's connection registered and refuses the new
one; the log says `[ws] ws connect failed` once and then nothing, forever. Our consumer lock
is machine-local and cannot see this — it correctly reports one holder. `channel feishu:
connected` is logged **because `start()` was called**, not because anything connected. A
message sent in that window is lost with no error. Today it cost four minutes and one
dropped message. Wait ~1 minute between kill and relaunch, and check the log for a
`connect failed` after the `connected` line.
