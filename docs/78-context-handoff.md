# 78. 建议换代：空闲时备好交接，人发 /new 时装入

INV-1190。来源：INV-1185 的对照调研（研究正文留在本地 research/，不入库）。

## 1. 问题

长私聊只有一种延续方式：越过阈值后原地压缩（[23](23-context-compaction.md)）。摘要会层层叠加，
到第四代以后整段原样搬运。`/new`（INV-672，[65](65-context-recovery-design.md)）可以换代，但换过去的新
上下文是空的，模型不知道刚才在做什么。

## 2. 决定

**系统不替人换代，只做两件事：建议换代，并备好交接。** 切换仍然只由人的 `/new` 触发，走 INV-672 的全部
同步检查。

自动换代的方案被两轮对抗评审驳回（§6）。没有人参与时，系统必须证明三件事：没有在途工作、记忆已经结算、
附件已经送达。这三件事在本系统里都没有权威数据源。

## 3. 备好交接（`context-steward.ts`，全部可丢弃）

- **触发**：私聊渠道任务的回复和文件都已投递、任务已结算之后，`ChannelManager` 发出 `contextIdle` 候选。
  候选不等于授权。
- **前置条件**：
  - 会话类型与 `/new` 相同，且 mode 为 normal；
  - 活动窗口不小于 `triggerTokens × 0.7`，或摘要已到第 2 代；
  - 同一会话 30 分钟冷却；
  - 当前上下文还没有有效草稿。
- **快照**：在第一次 await 之前抓取，内容包括 epoch、mode、转写长度、尾部 hash、计划/待办 hash，以及
  人的原话。模型读到的转写每条都带 ReadHistory 标签 `e{epoch}#{i}`。
- **管家**：`askBounded`。无工具，限定输出上限和超时，计费类别为 `steward`。管家只回答 switch 或 compact；
  无法判断或出错时一律按 compact 处理。
- **笔记**：固定 8 个英文标题，由代码校验，失败重试一次，再失败就放弃。笔记引用的标签逐个核对确实存在
  （只防编造的编号，不证明内容有据）。
- **草稿**：存到 `<transcript>.epochs/drafts/<epoch>.json`。如果写入时上下文已经变了，就拒绝写入，
  旧笔记永远不会被当成当前的。
- **建议**：每个 epoch 至多一条，用持久闩控制。建议走 INV-535 共享预算 `FollowUpBudget`，与预算在同一个
  tick 里预留，投递成功后才计入。建议的措辞是有条件的。

## 4. 人发 /new 时（`context-recovery.ts` + `context-epoch.ts`）

- **何时采用草稿**：只有请求 mode 和当前 mode 都是 normal，且草稿快照与当前上下文完全一致时才采用。
  `/new --clean` 永远不带交接。草稿过期时照常切换，回复里说明原因。
- **事务**：`advance(..., { opening })` 的顺序如下：
  1. staging 写入并读回校验，失败就不带交接，做普通切换；
  2. durable prepare；
  3. 迁移 legacy 文件（保留目录 fence）；
  4. 安装开场条目：已经装好且完整的保留；staging 有效的就写入；两者都不成立才写占位；
  5. fsync 涉及的目录；
  6. 最后才发布新 epoch。

  prepare 落盘之后只向前，不回退。`read()` 恢复时走同一序列。掉电持久性按这个 fsync 设计实现，但尚未实测。
- **回复**：首次回复和重放回复都根据记录下来的实际安装结果（handoff / placeholder）来写。

## 5. 显示

开场条目是一条 `summary` 条目，带 `handoff` 字段。模型请求按摘要和人的原话渲染（INV-1187）。网页把它显示为
一行安静的宿主条目（"carried over from the previous context"），不显示为人说的话。跨 epoch 的历史视图不在
本项范围内。

## 6. 评审记录

- v1（自动换代、压缩时触发）驳回，6 条 P1：
  - 与 busy 规则矛盾；
  - 首次迁移有崩溃窗口；
  - fsync 不足；
  - 用长度判断快照不可靠；
  - 换代会丢记忆抽取（另立 bug INV-1214，已修）；
  - 锚点会被重定向（INV-1187 中已修）。
- v2（空闲触发、settle）驳回，3 条 P1、2 条 P2：
  - prepare 之后回退会毁掉迁移；
  - settle 证明不了记忆已结算；
  - outbox 判空不可靠；
  - 跨 epoch 的 UI 身份；
  - 锚点会被改写。
- v3（建议换代）有条件通过，5 处修改均已并入：
  - 新 epoch 最后发布；
  - clean 不带交接；
  - 快照在 await 之前抓取并保留原始标签；
  - 建议走共享预算；
  - 回复按实际安装结果写。

## 7. 验证

- hermetic 测试：
  - `context-epoch.test.ts`：故障注入；
  - `context-recovery.test.ts`：采用、过期、clean、阻塞；
  - `context-steward.test.ts`：各条放弃路径、闩、预算、上下文变动、端到端；
  - `transcript.test.ts`：显示。
- 真模型一致率：`scripts/steward-eval.mjs`，`src/host/fixtures/steward-tails.json` 中有 22 段带标注的尾巴，
  在 MiniMax-M3 上运行，不进 `npm test`。2026-10-15 的结果：

  | 提示词 | 一致 | 误建议（应为 compact 却判为 switch） | 输入/输出 token |
  |---|---|---|---|
  | 初版（直接判断） | 15/22 | 6 | 6205 / 612 |
  | 先逐项核对再判断，第 1 次 | 19/22 | 3 | 10334 / 1330 |
  | 先逐项核对再判断，第 2 次 | 18/22 | 2 | 4336 / 1483 |

  剩下的错误集中在两类：一是"声称做完但漏了一部分"；二是暂停或交接时判断偏保守。误建议的代价是多发一条
  建议消息（受 INV-535 预算约束），草稿只在人发 `/new` 时才会用上。
- 交接连续性：`scripts/handoff-eval.mjs`，不进 `npm test`。它用 3 段真实长会话，只读 `~/.agentbox`：
  413 条/6 次压缩、434 条/10 次、164 条/2 次。对每段会话：
  1. 按 steward 的方式写交接笔记，带上人的原话；
  2. 另一个"出题人"读同一视图，出 6 道"继续干活必须知道"的题，覆盖约束、决定、确切事实、未完事项、下一步；
  3. 两个答题人分别只拿交接，或只拿最新一份压缩摘要作答；
  4. 评分人按 0/1/2 打分。

  写、出题、答、评都用 MiniMax-M3。2026-10-16 跑了三次：

  | 运行 | 交接 | 仅最新压缩摘要 |
  |---|---|---|
  | 1（评分解析失败，作废） | — | — |
  | 2 | 33/36 | 0/36 |
  | 3 | 23/36 | 0/36 |

  - 第 3 次的 4 个 0 分题，答案全都在笔记里：长期方案、≥3 周的 review 任务 t70/t74/t120/t182/t185、
    AskUser 选项、流水线顺序。丢分出在答题人。它被要求"不知道就说 unknown"，于是在长笔记里漏看。
    有几个 1 分是评分偏严，比如 UUID 全对仍只给 1 分。
  - 有一次答题人把 UUID 抄坏了（`feeba-3feeba8ddb5a1`），笔记里是对的。确切值要靠 ReadHistory 回查，
    不能只靠复述。
  - "仅摘要" 0 分说明题目考的是摘要之后的尾巴。不带交接的 `/new` 恰好丢的就是这部分，交接把它带了过去。
    这个对照只能说明这一点，不代表摘要本身的质量。
  - 局限：
    - 题目由同一个便宜模型出、同一个模型评，三次之间分差 10 分。
    - 答题人是 M3，不是生产主模型。
    - 每段只出 6 题。

  结论：笔记写得全，读的一方是瓶颈。这批结果不支持再调写笔记的提示词。
